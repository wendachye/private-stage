# Free cloud hosting research — 29 October 2026

**Oracle Cloud Always Free Ampere A1 is the strongest candidate for a free deployment of the current complete application.** This is a fit assessment, not a deployed or capacity-tested result. Account eligibility, an available Always Free shape in the selected home region, and representative media testing are still required. No account, payment, DNS, cloud resource, credential or running application was changed for this research.

## What has to be hosted

Private Stage currently combines Next.js and Fastify in one long-running Node 24 process, with authenticated SSE/WebSocket connections, file-backed SQLite and an in-process publication ledger. The supported boundary has one app/database/gateway instance and a self-hosted LiveKit server. The direct SFU signaling/API endpoint must remain private behind the application gateway; merely hosting the Next.js pages is incomplete. These requirements come from the current [migration plan](cloud-migration.md), [media trust boundary](media-enforcement.md#network-and-version-boundary), [Node engine requirement](../package.json) and [configuration](../backend/src/config.ts).

## Oracle details and caveats

Always Free compute must be in the tenancy's **home region**. Oracle documents possible out-of-host-capacity failures. Idle instances may be reclaimed after a seven-day period with CPU p95 below 20%, network below 20%, and A1 memory below 20%. Its free storage allowance covers boot and block volumes together, with at most five free volume backups. [Always Free resources](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm)

Always Free is not a time-limited trial; Oracle also offers a separate $300/30-day trial. Signup uses a qualifying credit/debit card for verification, and free-only use has no SLA or Oracle Support. Idle accounts can be suspended. Staying within Always Free resources after trial expiry is essential. [Oracle FAQ](https://www.oracle.com/cloud/free/faq/)

The current free-only entitlement is **2 OCPU/12 GB**, not the older widely quoted 4 OCPU/24 GB. Oracle's separate price list says **paid tenancies** get the first 3,000 OCPU-hours and 18,000 GB-hours monthly free. That does not authorize upgrading this user's account or assuming the larger allowance applies to a free-only tenancy. [Price list](https://www.oracle.com/cloud/price-list/)

Oracle lists live Malaysia West and Singapore regions; a region being live does not establish that its signup flow offers a free A1 shape or that capacity is available. Prefer a nearby eligible region only after checking those facts; do not promise stock or latency. [Region list](https://www.oracle.com/apac/cloud/public-cloud-regions/)

Arm is plausible for the current stack: Node 24.18.0 has an official Linux ARM64 binary, and the pinned `livekit/livekit-server:v1.13.11` image lists Linux ARM64. This establishes published runtime/image availability, not a successful migration of all npm dependencies. Build and test on Linux; do not copy Windows `node_modules`. [Node binary](https://nodejs.org/en/download/archive/v24.18.0), [LiveKit image architectures](https://hub.docker.com/r/livekit/livekit-server/tags)

## Why the media allowance matters

The app's Balanced setting caps each screen video at 1.5 Mbps; Detailed uses 3 Mbps. Actual bandwidth depends on content and subscription/adaptive-layer decisions. [Current capture settings](../frontend/client/media.tsx)

Illustration, not a measurement: 15 connected participants consume 900 participant-minutes per room-hour, so 5,000 minutes cover about **5.56 room-hours** before considering bandwidth. If 12 audience members each receive three 1.5 Mbps screen tracks continuously, that video alone is **24.3 GB/hour**: `12 × 3 × 1.5 Mbps × 3600 ÷ 8 ÷ 1000`. Other presenters' received tracks, audio, retransmissions and overhead are additional. Under that assumed bitrate, a 50 GB downstream allowance is about **two hours or less**, not 5.56 hours. Adaptive delivery can make actual usage lower; no provider capacity or precise bill is predicted. Source quotas: [LiveKit Build limits](https://docs.livekit.io/deploy/admin/quotas-and-limits/).

## Deployment boundary and next decision

For the current design, the simplest candidate is one eligible Oracle A1 Linux VM with durable storage: HTTPS reverse proxy → app/gateway; SFU signaling stays private, while approved media ports have a validated public route. LiveKit documents API/WebSocket 7880 behind TLS termination, ICE TCP 7881, and UDP 7882 mux or the configured UDP range; TURN requires its own setup. Public website HTTPS by itself does not establish WebRTC reachability. Resolve the HTTPS/TURN port-443 topology before deployment. [LiveKit firewall ports](https://docs.livekit.io/transport/self-hosting/ports-firewall/), [project migration procedure](cloud-migration.md).

Switching to LiveKit Cloud would expose a separately public signaling service. The current app issues a LiveKit-valid browser JWT and depends on its gateway being the exclusive ingress; merely changing the server URL would weaken that assumption. Adapt the credential/ingress boundary and retest direct connection, moderation, source-count limits and revocation first. This is a source-code architecture inference, not an exploit performed against a cloud account. [Current enforcement design](media-enforcement.md)

Before provisioning: confirm signup eligibility and available Always Free shape, region and public addressing; review the exact selected resource estimate; prepare Linux supervision, protected persistent data/backups, trusted TLS, DNS and Discord callback; then migrate a closed consistent snapshot and run real external/phone/capacity tests. A custom domain or a larger paid resource is not included in a provider's compute allowance. No signup, paid-plan upgrade, public exposure or deployment has been performed or authorized by this research request.
